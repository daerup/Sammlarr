[[section-runtime-view]]
== Runtime View

Four scenarios: resolving a title (the one the others build on), feed preview, a feed run through
the job queue, and wantlist sync/push. Each runs across the layers through `Contracts`, with
providers resolved by keyed DI.

=== Resolving a title

Turning an external reference (a TMDB/IMDb id or a bare title) into the right library row, and the
Plex id it can be pushed under, is where correctness hinges: a wrong match corrupts every list the
title appears in. Two phases: A settles _identity_ (which library row), B fills in _metadata_.

[mermaid]
....
sequenceDiagram
  actor C as Caller (feed / sync / trending)
  participant MS as IMediaService
  participant DB as Library (IMediaRepository)
  participant IC as Id converter
  participant MR as Metadata resolver

  C->>MS: IdentifyWithDetailsAsync(external ids + hints)
  MS->>DB: GetByExternalsAsync (one batched read)
  alt in library and fresh
    DB-->>MS: stored title
  else missing or stale
    MS->>IC: Phase A, resolve ids to an identity
    IC-->>MS: canonical identity (or unmatched)
    MS->>MR: Phase B, fill metadata
    MR->>DB: upsert (write-behind, on flush)
    MR-->>MS: IdentifiedMedia
  end
  MS-->>C: MediaLookup
....

The first lookup is the library itself (one batched `GetByExternalsAsync`); a fresh row is
returned as is (fresh = 7 days for a complete row or one whose gaps are all confirmed, 1 hour for
any other partial row). Only a missing or stale title runs the two phases.

==== Phase A: ids to a Plex identity

`MediaIdResolver` resolves the ids along the cheapest open path of id lookups to the target
(see Provider routing in <<section-concepts>>). The target is the provider the active sink addresses
that title's type by (`IMediaSink.AddressedBy`): Plex for every type today, so an MDBList or TMDB
reference is converted to a Plex id, the only id the wantlist can push. A type the sink cannot address
fails as unmatched. Plex looks up a Plex id and searches by the title hints. TMDB answers a TMDB id with its
detail, whose appended `external_ids` carry the IMDb and TheTVDB ids, and an IMDb or TheTVDB id through `find`.
Every TMDB answer also carries the original title, so a Plex search can follow it.

[mermaid]
....
sequenceDiagram
  participant MS as IMediaService
  participant NC as Unmatched cache
  participant IC as Plex converter
  participant PX as Plex

  MS->>NC: known unmatched? (skip providers if cached)
  MS->>IC: LookUpAsync(a Plex id, or the hints and known ids)
  alt candidate already has a Plex id
    IC->>PX: look up externals by that id
    PX-->>IC: external ids
  else only foreign ids (TMDB / IMDb)
    IC->>PX: search by title hint
    PX-->>IC: search hits
    loop each hit
      IC->>PX: look up the hit's externals
      PX-->>IC: its external ids
    end
    Note over IC,PX: keep the hit whose externals<br/>contain one of the known ids
  end
  alt a hit matched
    IC-->>MS: canonical identity
  else nothing matched
    IC-->>MS: unmatched
    MS->>NC: cache unmatched (1h), unless a path was blocked or unavailable
  end
....

A title match is confirmed by id, never trusted on the title alone: Plex is searched by the hint,
each hit's externals are looked up, and the first hit whose externals contain an original id wins
(if the hint finds nothing, it retries with TMDB's title). A negative cache of known-unmatched ids
(kept an hour) short-circuits repeats before any provider call. Resolved ids pass through the
coordinator (not shown), which merges them against existing rows so one title can't become two
library ids.

==== Phase B: metadata

Metadata comes from the search provider first (Plex), then from the open enricher that fills the
most missing fields, one at a time, until the record is complete. The rating counts as one of those
fields, filled by an enricher whose `Fills` include `MediaField.Rating` (today TMDB). Writes are
batched write-behind (one identity + one metadata upsert per run). Two failure behaviours matter: an
unmatched candidate becomes `UnmatchedMedia` (surfaced, never persisted); and when a provider is down
or rate-limiting the title shows as "not found" for that run but is not cached unmatched, so the next
run retries it (see <<section-technical-risks>>).

=== Feed preview

The user edits a feed in the editor and previews it. The result is computed live and never
written anywhere; it just shows what the feed would resolve to right now.

[mermaid]
....
sequenceDiagram
  actor U as User
  participant P as Feeds editor (UI)
  participant F as IFeedProvider (MDBList)
  participant M as MDBList
  participant R as IMediaService (+ cache, DB)
  participant E as IFeedRunPlanner
  participant W as Wantlist + blocklist

  U->>P: edit feed, preview
  P->>F: GetFeedItemsAsync, keyed by FeedProvider
  loop each page, while X-Has-More
    F->>M: GET list items (resilience pipeline)
    M-->>F: entries
    F->>R: IdentifyWithDetailsAsync(externals)
    R-->>F: MediaLookup (matched or unmatched)
    F-->>P: stream items
  end
  loop as items arrive, then once more when settled
    P->>E: PlanAsync(DraftFeed(feed, RawFeedLoad(items so far, Partial or Complete)))
    E->>W: wantlist ids, blocklist ids, this feed's own slice
    E->>E: classify each row, then FeedPlans.Compute
    E-->>P: FeedPlanResult (an AppendPlan or MirrorPlan, or FeedPlanFailed)
  end
  P-->>U: tiles, stat badges, unmatched list
....

`IFeedProvider` is resolved by the feed's `FeedProvider` key. Each entry is resolved to a
`MediaLookup` by the pipeline above, so a preview reuses cached rows and rarely hits every
provider. On a circuit-breaker trip or timeout the client raises `ProviderUnavailableException`;
the panel shows partial results and a retry rather than failing the whole preview.

The preview does not classify for itself. It goes through `IFeedRunPlanner`, which reads the
enrollment collections, classifies the rows and hands them to the pure `FeedPlans.Compute`.
`IFeedRunEngine` plans through that same planner before it applies anything, so a preview and a
run cannot drift apart about what a run would do: they are the same call. The panel re-plans as
items arrive, on a geometric schedule (after items 1, 2, 4, 8 …) rather than on a timer, which
keeps total classification work linear in the size of the list.

Every call made before the fetch settles passes `Completeness.Partial`. The planner then reports
`Conclusiveness.StillLoading` and withholds removals, because absence from a list that is still
loading is not evidence that an item has left it. The panel keeps reporting a partial source for
as long as it is showing truncated results after a provider outage, so tightening a filter
against a half-loaded list cannot propose deleting the part that never arrived.

=== Feed runs and the job queue

A run applies what the preview showed. Feed runs and wantlist syncs never execute where they are
requested: every request becomes a row in the `Jobs` table, and one runner works through the rows
one at a time.

[mermaid]
....
sequenceDiagram
  participant T as TickerQ (cron)
  actor U as User (Run now / Sync)
  participant Q as IJobQueue
  participant J as Jobs table
  participant R as JobRunner
  participant E as FeedRunEngine
  participant W as IWantlistService
  participant SE as WantlistSyncEngine

  T->>Q: cron fires: RunFeed(feed, Scheduled), as the feed's owner
  U->>Q: RunFeed(feed, Manual)
  Q->>J: insert, or fold into the feed's pending row
  R->>J: take the oldest Queued row, mark Running
  R->>Q: a scheduled run starts: SyncWantlist(ScheduledFeedTrigger)
  Q->>J: one Waiting sync per owner, due after the grace period
  R->>E: dispatch in a fresh scope, as the job's owner
  E->>E: plan (the same planner as the preview)
  E->>W: apply adds and owned drops, recorded in the run log
  Note over W: outbox rows written, nothing sent to Plex yet
  Note over J: further runs push the sync back,<br/>never past its deadline (first arming + MaxWait)
  J->>R: the alarm releases the sync when due
  R->>SE: dispatch the sync
....

TickerQ owns only the _when_: each scheduled feed has one cron ticker (keyed by the feed id,
created, updated or deleted as the feed is saved), and its function does nothing but enqueue a
`RunFeed` under the feed owner's identity. The runner decides what runs next and the UI reads the
rows, which is how the Home dashboard shows what is running, queued and waiting.

Enqueueing coalesces by kind, key and owner, so a request never duplicates one already pending: a
second run of the same feed folds into the pending or running one, and a sync folds into the
owner's pending sync. A scheduled run (or a manual run with _sync when done_) arms the sync as it
starts, `Grace` (2 minutes) in the future, and every later such run pushes it back, never past
its deadline, `MaxWait` (30 minutes) after it was first armed. So N feed runs in a window produce
one sync, and a feed that adds a title and another that removes it cancel out in the outbox before
anything reaches Plex. A sync only counts down its grace while none of its owner's syncing runs is
queued: once one is, the sync is `Queued` behind it, and when that run starts and arms the sync
again, the grace starts over. A plain manual run, from the Feeds page, neither arms nor holds the
sync. A manual Sync skips the grace: it moves the sync's deadline to now, so it runs as soon as the
runs already queued ahead of it finish, no later run can push it back, and runs queued after it
wait their turn.

A future row is `Waiting`; a `JobAlarm` timer moves it to `Queued` when due and nudges the runner,
so a deferred sync runs on time without the runner polling. A handler that throws ends `Failed`;
there is no automatic retry. A row still `Running` when the app starts was abandoned by the
previous process (there is only one runner), so startup puts it back to `Queued`.

The owner can cancel a job that has not started, from Up Next on the Home page: a `Waiting` or
`Queued` row ends `Cancelled` and never runs. The cancel only takes a row still in one of those two
states, so a job the runner claims at the same moment runs instead, and the owner is told it had
already started. Cancelling a feed run leaves a sync queued behind it in place, and a schedule
still fires as usual.

The engine plans through the same planner as the preview, before it records the run, so a run
does what a preview taken at that moment would show. Mirror removals follow the preview's rule: a load that did not finish, or came back empty, is not
conclusive and drops nothing, and an item is only removed after it has been missing for the
feed's absence threshold of conclusive runs.

=== Wantlist sync and push to Plex

Adding a title and pushing it to Plex are two separate steps. An add writes the local row and
queues the change in the outbox; the push happens inside the next sync, which drains the outbox
inline. A change that fails stays in the outbox and is retried by the sync after it.

[mermaid]
....
sequenceDiagram
  actor U as User
  participant W as UI (Wantlist / Browse)
  participant S as IWantlistService
  participant DB as DB (wantlist + outbox)
  participant SE as WantlistSyncEngine (a job)
  participant PX as IMediaSink (Plex)
  participant Plex as Plex

  Note over U,DB: Add: local only, no Plex call
  U->>W: add title
  W->>S: AddAsync(ids, origin)
  S->>DB: insert wantlist row + outbox row (Pending)
  S-->>W: item shows a Pending push dot

  Note over U,Plex: Sync: pull, then push pending changes
  SE->>PX: GetAsync
  PX->>Plex: read the Plex watchlist
  PX-->>SE: its items matched to titles, plus the unmatched
  SE->>DB: apply remote adds and removes
  SE->>DB: read Pending outbox rows, grouped by add / remove
  SE->>PX: ApplyAsync per group, as title ids
  PX->>Plex: PUT per item, by its Plex id
  PX-->>SE: ack per title
  alt acked
    SE->>DB: drop outbox row
    SE-->>W: event Pushed (dot clears)
  else not acked
    SE->>DB: record attempt
    SE-->>W: event Retrying, or Abandoned on the fifth attempt
  end
  SE->>SE: one sync notification with what reached Plex
....

Adds and removes cancel each other in the outbox (adding cancels a pending removal; removing
cancels an un-pushed add), so opposing changes never reach Plex. Each item gets five attempts, one
per sync; the fifth failure marks it `Failed`, which is terminal: later syncs no longer push it,
but still count it as intent, so an abandoned add is not mistaken for a remote deletion. An item
the sink cannot address (for Plex, one with no Plex id) is abandoned at once. Per-item status
reaches the open page as in-process events, and the sync ends with one notification that reports
what actually reached Plex, not what was queued. The engine holds a per-user gate, so two syncs
for one user never overlap.

=== Other flows

Two flows are worth a mention but not a diagram of their own. Notifications are the one thing on
Wolverine's durable queue: a finished sync or feed run publishes one notification, a handler fans
it out to each matching subscription, and each is rendered from a Fluid template and delivered on
its own retry schedule (1, 5 and 15 minutes, then an hour); the WebUi channel delivers it as an
in-app toast. Plex sign-in is a standard OAuth PIN flow; its notable parts, the app-owned
`User`, the first user becoming Admin, the open or closed registration gate, and per-request
session revalidation, are covered in <<section-concepts>>.
