== Runtime View

Three scenarios: resolving a title (the one the others build on), feed preview, and watchlist
sync/push. Each runs across the layers through `Contracts`, with providers resolved by keyed DI.

=== Resolving a title

Turning an external reference (a TMDB/IMDb id or a bare title) into the right library row, and the
Plex id it can be pushed under, is where correctness hinges: a wrong match corrupts every list the
title appears in. Two phases: A settles _identity_ (which library row), B fills in _metadata_.

[mermaid]
....
sequenceDiagram
  actor C as Caller (feed / sync / trending)
  participant MS as IMediaService
  participant DB as Library (IMediaRepository)
  participant IC as Id converter
  participant MR as Metadata resolver

  C->>MS: ResolveDetailsAsync(external ids + hints)
  MS->>DB: GetByExternalsAsync (one batched read)
  alt in library and fresh
    DB-->>MS: stored title
  else missing or stale
    MS->>IC: Phase A, resolve ids to an identity
    IC-->>MS: canonical identity (or unmatched)
    MS->>MR: Phase B, fill metadata
    MR->>DB: upsert (write-behind, on flush)
    MR-->>MS: IdentifiedMedia
  end
  MS-->>C: MediaLookup
....

The first lookup is the library itself (one batched `GetByExternalsAsync`); a fresh row is
returned as is (fresh = 7 days for a complete row, 1 hour for a partial one). Only a missing or
stale title runs the two phases.

==== Phase A: ids to a Plex identity

One `IExternalIdConverter`, chosen by the target provider, resolves the ids. The TMDB, IMDb and
TheTVDB targets just pass ids through; the Plex target does the work, since an MDBList or TMDB
reference has no Plex id and the watchlist can only push a Plex id.

[mermaid]
....
sequenceDiagram
  participant MS as IMediaService
  participant NC as Unresolved cache
  participant IC as Plex converter
  participant PX as Plex

  MS->>NC: known unmatched? (skip providers if cached)
  MS->>IC: ConvertAsync(ids, title hint)
  alt candidate already has a Plex id
    IC->>PX: look up externals by that id
    PX-->>IC: external ids
  else only foreign ids (TMDB / IMDb)
    IC->>PX: search by title hint
    PX-->>IC: search hits
    loop each hit
      IC->>PX: look up the hit's externals
      PX-->>IC: its external ids
    end
    Note over IC,PX: keep the hit whose externals<br/>contain one of the original ids
  end
  alt a hit matched
    IC-->>MS: canonical identity
  else nothing matched
    IC-->>MS: unresolved
    MS->>NC: cache unmatched (1h)
  end
....

A title match is confirmed by id, never trusted on the title alone: Plex is searched by the hint,
each hit's externals are looked up, and the first hit whose externals contain an original id wins
(if the hint finds nothing, it retries with TMDB's title). A negative cache of known-unmatched ids
(kept an hour) short-circuits repeats before any provider call. Resolved ids pass through the
coordinator (not shown), which merges them against existing rows so one title can't become two
library ids.

==== Phase B: metadata

Metadata comes from the search provider first (Plex), then an enricher chain (TMDB) until the
record is complete, then ratings (TMDB); writes are batched write-behind (one identity + one
metadata upsert per run). Two failure behaviours matter: an unresolved candidate becomes
`UnmatchedMedia` (surfaced, never persisted); and when a provider is down or rate-limiting the id
is cached unmatched for the hour, which is why a Plex 429 storm reports existing titles as "not
found" (see <<section-technical-risks>>).

=== Feed preview

The user edits a feed in the editor and previews it. The result is computed live and never
written anywhere; it just shows what the feed would resolve to right now.

[mermaid]
....
sequenceDiagram
  actor U as User
  participant P as Feeds editor (UI)
  participant F as IFeedService (MDBList)
  participant M as MDBList
  participant R as IMediaService (+ cache, DB)
  participant Q as IQueryProcessor

  U->>P: edit feed, preview
  P->>F: GetFeedItemsAsync, keyed by FeedProvider
  loop each page, while X-Has-More
    F->>M: GET list items (resilience pipeline)
    M-->>F: entries
    F->>R: ResolveDetailsAsync(externals)
    R-->>F: MediaLookup (matched or unmatched)
    F-->>P: stream items
  end
  P->>Q: ExecuteAsync(filter, sort, limit)
  Q-->>P: rows (included / bypassed / culled / truncated)
  P-->>U: tiles, stat badges, unresolved list
....

`IFeedService` is resolved by the feed's `FeedProvider` key. Each entry is resolved to a
`MediaLookup` by the pipeline above, so a preview reuses cached rows and rarely hits every
provider. On a circuit-breaker trip or timeout the client raises `ProviderUnavailableException`;
the panel shows partial results and a retry rather than failing the whole preview.

NOTE: Only preview exists today. A scheduler that runs feeds on a cron and reconciles the
results into the watchlist is planned, not built (see <<section-technical-risks>>). Titles enter
the watchlist by manual add or by sync, below.

=== Watchlist sync and push to Plex

Adding a title and pushing it to Plex are two separate steps. An add writes the local row and
queues the change; the push to Plex happens on the next sync, drained from a durable outbox so
it survives restarts and provider outages.

[mermaid]
....
sequenceDiagram
  actor U as User
  participant W as UI (Watchlist / Browse)
  participant S as IWatchlistService
  participant DB as DB (watchlist + outbox)
  participant SE as WatchlistSyncEngine
  participant WO as Wolverine queue (SQLite)
  participant H as Push handler
  participant PX as IWatchlistProvider (Plex)
  participant Plex as Plex

  Note over U,DB: Add: local only, no Plex call
  U->>W: add title
  W->>S: AddToWatchlistAsync(ids, origin)
  S->>DB: insert watchlist row + outbox row (Pending)
  S-->>W: item shows a Pending push dot

  Note over U,Plex: Sync: push pending changes
  U->>SE: Sync
  SE->>WO: publish WatchlistPushRequest per item
  WO->>H: deliver (durable, retried)
  H->>DB: find pending row (skip if already gone)
  H->>PX: AddToWatchlistAsync(external id)
  PX->>Plex: PUT watchlist
  Plex-->>PX: ack
  alt success
    H->>DB: drop outbox row
    H-->>W: event Pushed (dot clears)
  else failure
    H->>DB: record attempt
    H-->>W: event Retrying or Failed
    H->>WO: throw, re-queued with cooldown
  end
....

Adds and removes cancel each other in the queue (adding cancels a pending removal; removing
cancels an un-pushed add); if the outbox row is gone when a message runs, the handler no-ops (a
harmless "ghost"). Retries are two-level: the handler caps at five attempts and records per-item
status, and Wolverine re-delivers on a cooldown (5s, 15s, 30s, 1min). Status reaches the open page
through an in-process event feed.

=== Other flows

Two flows are worth a mention but not a diagram of their own. Notifications ride the same durable
outbox as the watchlist push: a sync raises one `WatchlistSyncedEvent`, a handler fans it out to
each matching subscription, and each is rendered from a Fluid template and delivered on its own
retry schedule. Plex sign-in is a standard OAuth PIN flow; its notable parts, the app-owned
`User`, the first user becoming Admin, the open or closed registration gate, and per-request
session revalidation, are covered in <<section-concepts>>.
