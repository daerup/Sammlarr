[[section-runtime-view]]
== Runtime View

Four scenarios: loading a list (the one the others build on), feed preview, a feed run through
the job queue, and wantlist sync/push. Each runs across the layers through `Contracts`, with
providers resolved by keyed DI.

=== Loading a list

Turning a list's entries (TMDB, IMDb or other ids, with title hints) into the right library rows, and the id the
sink adds each title by, is where correctness hinges: a wrong match corrupts every list the title appears in. A feed
service streams its entries into `IMediaService.LoadListAsync`, which hands each title back with its list position
(`Listed<MediaMatchResult>`) as soon as it settles. Four ideas carry the load: bursts, chains, lanes and claims.

[mermaid]
....
flowchart LR
  SRC[List source<br/>pages as they arrive] --> BURST[Burst<br/>what the source has ready]
  BURST --> LIB[(Library read<br/>once per burst)]
  BURST -.->|misses| PRIME[Primers<br/>MDBList lane, datasets]
  LIB --> CHAIN{{one chain per title}}
  CHAIN -->|partly stored or unknown| IDS[Resolve ids]
  IDS --> CLAIM[(Claim the identity)]
  CLAIM -->|claimed| DET[Details<br/>reused while fresh]
  CLAIM -->|conflicted| CON[Settle: conflict]
  CHAIN -->|stored with the sink's id| DET
  DET --> OUT[Settle with<br/>its list position]
  IDS -.->|ask| LANES[[Lanes<br/>one per service route]]
  DET -.->|ask| LANES
....

A _burst_ is everything the source yields without waiting (`BurstsAsync`): one page of an MDBList list, one page of
TMDB results. `ListLoad` reads the library once per burst (`IMediaRepository.GetByExternalsAsync`: one flat,
parameterized query per table inside one read snapshot). It then hands the burst's titles, each with its stored copy, to
the primers (`BurstPrimers`), and each primer primes the ones it can help. MDBList's primer queues each title that needs a field MDBList fills on its batching lane and returns
at once; the anime id map's and IMDb ratings file's primers (`AnimeIdsInRun`, `ImdbRatingsInRun`) read their table once
for the whole burst. A primer is asked only for a service the user has connected, and a lane primer only while its lane
would take the ask in time. Every title of the burst waits for that read and those primes; MDBList's primer only
queues, so a blocked MDBList never holds a burst up.

Each title then runs its own _chain_ (`ListLoad.SettleAsync`) under `LaneClass.Title`, numbered by list position, so
earlier titles go first at every lane. Nothing caps how many chains run: the lanes pace each service, and a title that
needs nothing from a slow service settles without waiting for it. A chain settles exactly once, in its `finally`:
matched, not found, not found earlier, couldn't look up or conflict; a chain that throws settles couldn't look up, and
the load rethrows its exception once every chain has settled, so a feed run records the load as unfinished.
Titles leave as they settle, out of order, and the planner sorts them by position once. A `RunWatchdog` watches the
load: when no title has settled for `Sammlarr:FeedLoad:StallAfter` (3 minutes), it cancels the open chains, which settle
couldn't look up.

Each load runs in its own DI scope entered as its caller (`FeedRunPlanner`, the feed preview, each page of the
FillDetails job), so the per-load memos (`MdblistTitles`, `TmdbApi`, `AniListTitles`, `TraktTitles`, `AnimeIdsInRun`,
`ImdbRatingsInRun`) start empty for every load and are shared by the feed service and its chains.

==== Ids and the claim

`TitleIdentifier` starts from the stored titles the entry's ids hit. Ids on two stored titles go straight to an
unpinned claim, which conflicts and notes the pair (below). A stored title that holds the id the sink adds by is known: new ids from the list are added to it
through a pinned claim, and the chain goes on to its details. Any other title is resolved by `MediaIdResolver`, from
the list's ids plus the stored title's keys and hints, along the cheapest open path of id lookups to the target (see
Provider routing in <<section-concepts>>). The target is the provider the active sink addresses that title's type by
(`IMediaSink.AddressedBy`): Plex for every type when the wantlist syncs to Plex, so an MDBList or TMDB reference is
converted to a Plex id; TMDB for movies and TheTVDB for shows when it syncs to Radarr + Sonarr, the ids those apps add
by. A type the sink cannot address settles not found.

Plex finds its own id by the title's TMDB, IMDb or TheTVDB id through its match endpoint
(`library/metadata/matches?type=1|2&guid=tmdb://603` on the discover host), one call per title. A definitive answer by
one id answers that lookup for the title's other ids too (`ById.AsksOnce`), so a miss costs one Plex call and no
detour. A Plex id is read back through Plex's metadata endpoint for the title's other ids. TMDB answers a TMDB id with
its detail, whose appended `external_ids` carry the IMDb and TheTVDB ids, and an IMDb or TheTVDB id through `find`;
within a load, the id lookup and the details step share one read of a title's TMDB details.

[mermaid]
....
sequenceDiagram
  participant T as Title chain
  participant NC as Unmatched cache
  participant R as MediaIdResolver
  participant PX as Plex (match lane)
  participant IC as IIdentityClaims
  participant DB as Library

  T->>R: ResolveAsync(ids, target Plex)
  R->>NC: a miss cached within the hour?
  alt cached miss
    R-->>T: not found earlier
  else not cached
    R->>PX: library/metadata/matches?guid=tmdb://ID
    alt Plex id found
      PX-->>R: Plex id
      R-->>T: resolved ids and the services that gave them
      T->>IC: claim the identity keys
      IC->>DB: one transaction for every claim queued
      alt extends at most one stored title
        IC-->>T: Claimed(MediaId)
      else keys on two titles, or a second key of one source
        IC-->>T: Conflicted(owners)
      end
    else every route answered no match
      R->>NC: cache the miss (1 h)
      R-->>T: not found
    else a route unavailable, refused or faulted
      R-->>T: couldn't look up, nothing cached
    end
  end
....

A resolved title is claimed before it is handed out (`IIdentityClaims.ClaimAsync`), from its identity keys only; page
links never take part. The claim lane (`IdentityClaims`, one per scope) commits every claim queued meanwhile in one
transaction under the media write lock and decides each by the pure `ClaimRule`. A claim extends at most one stored
title and never merges two. It never adds a second key of one source or a key of another media type. A claim pinned to
a title drops the keys it cannot take instead of failing. Any other claim that would touch two stored titles, give a
title a second key of one source or a key of another media type, or that the one-key-per-source index refuses, comes
back `Conflicted` with the titles that hold its keys: the title settles
unmatched as a conflict (`UnmatchedReason.Conflict`, with `ConflictsWith`), and both stored titles stay as they are. A
claimed title is handed out only with its stored `MediaId`.

Every claim that meets two stored titles leaves a note in the same transaction (`IIdentityConflicts`, one row per
pair): a conflicted claim notes its first title against each other one, and a pinned claim notes its title against
each title holding a key it dropped (`Claimed.Disputed`). The note keeps the key that joined them and the services
behind the claim; it is due at once, and a pair met again only moves its `SeenAt`.

A title settles not found, and its ids are cached as unmatched for an hour, only when every route answered that it
has no such title. A route that was unavailable, refused by its lane or answered with something unusable settles the
title couldn't look up, and nothing is cached (see <<section-technical-risks>>). The cache short-circuits a repeat
before any provider call; the library is read before it, so a title stored within the hour is never hidden by it.

==== Details

A stored title is reused as it is unless the details fetcher would ask again: `Sammlarr:Housekeeping:FreshDays` (14 days) after its last refresh, or when a
field the load needs is missing and a service that is not resting could fill it (see Freshness in
<<section-glossary>>). A refresh asks the search setting's enricher first, then the open enricher that fills the
most missing detail fields, one at a time, until no open enricher can fill what is still missing; a blocked enricher whose
block ends within its `EnrichWait` (TMDB 15 s) is asked, and its lane holds the ask for at most the service's `MaxWait`
(TMDB 15 s) before it refuses it (see Provider routing in <<section-concepts>>). A gap fill starts from the
stored copy and its answers and asks only the enrichers that have not answered. The cache stores who answered and
what each could not give (`ProviderAnswer`), and a failure after sending as a failure with its backoff; a provider
that refused before sending, was skipped, or was never asked (no id for it, or the user has no key or sign-in for it)
still counts as not having answered. Every answer wins over the stored copy and each answer over the later ones (`first ?? second ?? ... ?? stored`),
so the stored copy only fills what no answer has; the next enricher is asked only while that still leaves a gap. A refresh
asks from scratch until its first answer and keeps a stored value only while a provider gave it within the last `FreshDays`
(`ProviderAnswer.AnsweredAt`), so a value removed upstream, or one whose provider is down or not connected, goes with
the first refresh 14 or more days after a provider last gave it. Each rating source counts as one of
those fields (`MediaFields` pairs the detail flags with a set of `RatingSource`): TMDB fills its own, Plex fills IMDb, Rotten Tomatoes and its copy of TMDB's.

Keys an enricher's answer adds are claimed for the title, pinned to it, after its details; a key the claim refuses is
dropped from the title. Changed details go to the load's `LibraryWriter`, which writes them as the run goes, at most
256 titles per transaction, and writes a failed group one title at a time. Two failure behaviours matter: an unmatched
title becomes `UnmatchedMedia` (surfaced, never persisted); and when no enricher can answer (down, blocked past its
wait or answering with errors), the title keeps its stored copy, marked `Stale` when the copy is due and its service
couldn't be reached, or, when nothing is stored and the service was unreachable, goes out with the list's own title.
Nothing is cached as not found, so the next load asks again.

=== Feed preview

The user edits a feed in the editor and previews it. The result is computed live and never
written anywhere; it just shows what the feed would load right now.

[mermaid]
....
sequenceDiagram
  actor U as User
  participant P as Feeds editor (UI)
  participant F as IFeedProvider (MDBList)
  participant M as MDBList
  participant R as IMediaService (+ cache, DB)
  participant E as IFeedRunPlanner
  participant W as Wantlist + blocklist

  U->>P: edit feed, preview
  P->>F: GetFeedItemsAsync(identifier, the draft's field needs), keyed by FeedProvider
  loop each page, while X-Has-More
    F->>M: GET list items (lane class Source)
    M-->>F: entries
    F->>R: LoadListAsync (the entries join the load's stream)
    R-->>F: each title with its list position, as it settles
    F-->>P: stream items
  end
  loop as items arrive, then once more when settled
    P->>E: PlanAsync(DraftFeed(feed, RawFeedLoad(items so far, Unfinished or Finished)))
    E->>W: wantlist ids, blocklist ids, this feed's own slice
    E->>E: classify each row, then FeedPlans.Compute
    E-->>P: FeedPlanResult (an AppendPlan or MirrorPlan, or FeedPlanFailed)
  end
  P-->>U: tiles, stat badges, unmatched list
....

`IFeedProvider` is resolved by the feed's `FeedProvider` key, inside a scope the panel opens as the signed-in user.
Each entry is loaded as a `MediaMatchResult` by the list load above, so a preview reuses stored rows and rarely asks
every provider. List pages read at `LaneClass.Source`, ahead of every title at the same lanes. When a list page cannot
be read because its service is unavailable, the feed service raises `RemoteUnavailableException`; the panel shows
partial results and a retry rather than failing the whole preview. Leaving the editor cancels the load, its replans
and its toasts.

The preview does not classify for itself. It goes through `IFeedRunPlanner`, which reads the
enrollment collections, classifies the rows and hands them to the pure `FeedPlans.Compute`. Each row
carries the feed's Sammlarr rating, resolved once per plan from the feed's `RatingStrategy` (else the
owner's default) over the available rating sources; the `Rating` and `Votes` filter and sort fields read it.
`IFeedRunEngine` plans through that same planner before it applies anything, so a preview and a
run cannot drift apart about what a run would do: they are the same call. The panel re-plans as
items arrive, on a geometric schedule (after items 1, 2, 4, 8 …) rather than on a timer, which
keeps total classification work linear in the size of the list.

Every call made before the fetch settles passes `FeedLoadState.Unfinished`. The planner then
reports `Conclusiveness.StillLoading` and withholds removals, because absence from a list that is
still loading is not evidence that an item has left it. The panel keeps reporting the load as
unfinished for as long as it is showing truncated results after a provider outage, so tightening
a filter against a half-loaded list cannot propose deleting the part that never arrived.

=== Feed runs and the job queue

A run applies what the preview showed. Feed runs and wantlist syncs never execute where they are
requested: every request becomes a row in the `Jobs` table, and one runner works through the rows
one at a time.

[mermaid]
....
sequenceDiagram
  participant T as TickerQ (cron)
  actor U as User (Run / Sync)
  participant Q as IJobQueue
  participant J as Jobs table
  participant R as JobRunner
  participant E as FeedRunEngine
  participant W as IWantlistService
  participant SE as WantlistSyncEngine

  T->>Q: cron fires: RunFeed(feed, Scheduled), as the feed's owner
  U->>Q: RunFeed(feed, Manual)
  Q->>J: insert, or fold into the feed's pending row
  R->>J: take the oldest Queued row, mark Running
  R->>Q: a scheduled run starts: SyncWantlist(ScheduledFeedTrigger)
  Q->>J: one Waiting sync per owner, due after the grace period
  R->>E: dispatch in a fresh scope, as the job's owner
  Note over E: opens the run's live trace;<br/>titles, hops and give-ups record into it
  E->>E: plan (the same planner as the preview)
  E->>W: apply adds and owned drops, recorded in the run log
  Note over W: outbox rows written, nothing sent to Plex yet
  Note over J: further runs push the sync back,<br/>never past its deadline (first arming + MaxWait)
  J->>R: the alarm releases the sync when due
  R->>SE: dispatch the sync
....

TickerQ owns only the _when_: each scheduled feed has one cron ticker (keyed by the feed id,
created, updated or deleted as the feed is saved), and its function does nothing but enqueue a
`RunFeed` under the feed owner's identity. The runner decides what runs next and the UI reads the
rows, which is how the Home dashboard shows what is running, queued and waiting.

Enqueueing coalesces by kind, key and owner, so a request never duplicates one already pending: a
second run of the same feed folds into the pending or running one, and a sync folds into the
owner's pending sync. A scheduled run (or a manual run with _sync when done_) arms the sync as it
starts, `Grace` (2 minutes) in the future, and every later such run pushes it back, never past
its deadline, `MaxWait` (30 minutes) after it was first armed. So N feed runs in a window produce
one sync, and a feed that adds a title and another that removes it cancel out in the outbox before
anything reaches Plex. A sync only counts down its grace while none of its owner's syncing runs is
queued: once one is, the sync is `Queued` behind it, and when that run starts and arms the sync
again, the grace starts over. A plain manual run, from the Feeds page, neither arms nor holds the
sync. A manual Sync skips the grace: it moves the sync's deadline to now, so it runs as soon as the
runs already queued ahead of it finish, no later run can push it back, and runs queued after it
wait their turn.

A future row is `Waiting`; a `JobAlarm` timer moves it to `Queued` when due and nudges the runner,
so a deferred sync runs on time without the runner polling. A handler that throws ends `Failed`;
there is no automatic retry. A row still `Running` when the app starts was abandoned by the
previous process (there is only one runner), so startup puts it back to `Queued`.

The owner can cancel a job that has not started, from Up Next on the Home page: a `Waiting` or
`Queued` row ends `Cancelled` and never runs. The cancel only takes a row still in one of those two
states, so a job the runner claims at the same moment runs instead, and the owner is told it had
already started. Cancelling a feed run leaves a sync queued behind it in place, and a schedule
still fires as usual.

The engine first saves the run as `Pending`, which run history shows as running. It then plans through the same
planner as the preview, so a run does what a preview taken at that moment would show, and applies the plan: each title
the sink can address is added, and one it cannot is recorded as unaddressable instead of failing the run. The run row
is completed in every case, with its calls; a run that throws or is cancelled ends `Stopped` with its reason, and
startup sweeps a `Pending` run that a crash left behind to `Stopped`. Mirror removals follow the preview's rule: a load
that did not finish, came back empty, or left a title Sammlarr couldn't look up is not conclusive and drops nothing. An
owned title missing from a conclusive run counts one more miss in `FeedAbsences`, and it is removed once it has been
missing for the feed's absence threshold of conclusive runs; an owned title in conflict, or served stale, counts as
seen.

A run also queues its owner's `FillDetails` job, as storing a key or a sign-in does. The job waits `FillDetailsGrace`
(5 minutes), stays behind any queued or waiting feed run or sync until it has waited `FillDetailsMaxWait` (30
minutes), and fills the missing fields of the owner's wantlisted and blocklisted titles 500 at a time at
`LaneClass.Background`. It asks only services that answer within `ShownWait` (5 seconds), and between pages it requeues
itself whenever another job is queued, so it never holds up a run or a sync.

While it runs, the engine holds the run's live trace open (`IFeedRunTrace.Start`, under the job owner's identity), and
identifying a title, asking a service and giving up on one record into it as spans; the owner watches them on the Feeds
page (<<section-concepts>>, Live run trace). The trace ends with the run's result and is dropped 30 seconds later;
afterwards the card's bar and the run log read the saved `FeedRun`, whose counts include the titles already known and
those not found earlier.

=== Wantlist sync and push to Plex

Adding a title and pushing it to Plex are two separate steps. An add writes the local row and
queues the change in the outbox; the push happens inside the next sync, which drains the outbox
inline. A change that fails stays in the outbox and is retried by the sync after it.

[mermaid]
....
sequenceDiagram
  actor U as User
  participant W as UI (Wantlist / Browse)
  participant S as IWantlistService
  participant DB as DB (wantlist + outbox)
  participant SE as WantlistSyncEngine (a job)
  participant PX as IMediaSink (Plex)
  participant Plex as Plex

  Note over U,DB: Add: local only, no Plex call
  U->>W: add title
  W->>S: AddAsync(ids, origin)
  S->>DB: insert wantlist row + outbox row (Pending)
  S-->>W: item shows a Pending push dot

  Note over U,Plex: Sync: pull, then push pending changes
  SE->>PX: GetAsync
  PX->>Plex: read the Plex watchlist
  PX-->>SE: its items matched to titles, plus the unmatched
  SE->>DB: apply remote adds and removes
  SE->>DB: read Pending outbox rows, grouped by add / remove
  SE->>PX: ApplyAsync per group, as title ids
  PX->>Plex: PUT per item, by its Plex id
  PX-->>SE: ack per title
  alt acked
    SE->>DB: drop outbox row
    SE-->>W: event Pushed (dot clears)
  else not acked
    SE->>DB: record attempt
    SE-->>W: event Retrying, or Abandoned on the fifth attempt
  end
  SE->>SE: one sync notification with what reached Plex
....

Adds and removes cancel each other in the outbox (adding cancels a pending removal; removing
cancels an un-pushed add), so opposing changes never reach Plex. Each item gets five attempts, one
per sync; the fifth failure marks it `Failed`, which is terminal: later syncs no longer push it,
but still count it as intent, so an abandoned add is not mistaken for a remote deletion. An item
the sink cannot address (for Plex, one with no Plex id) is abandoned at once. Per-item status
reaches the open page as in-process events, and the sync ends with one notification that reports
what actually reached Plex, not what was queued. The engine holds a per-user gate, so two syncs
for one user never overlap.

On Radarr + Sonarr each app is read on its own. When one cannot be read and the other can, the sync
plans only the titles whose type the answering app holds: the down app's titles stay out of the pull
(otherwise the plan would read them as removed in the app and pull them off the wantlist) and out of
the drain (their outbox entries wait, with no attempt counted), and the sync announces the failure for
the down app next to its usual notification. Only when neither app can be read does the whole sync
stop.

Switching the sink (Plex to Radarr + Sonarr or back, `ISinkSwitch`) holds every user's gate for the
whole switch and refuses if a sync is running. Under each user it gives every wantlist, outbox and
blocklist title the id the new sink addresses it by (re-identifying from the ids the title already
carries), then queues every wantlist title as an add, and only then stores the new sink. Without the
queued adds the first sync would read the new sink, find none of the titles and remove them all. A
title no lookup can convert is counted and acks unaddressable on its first push; the cache purge
keeps every id of a title that lacks the sink's id, so a later switch can still convert it.

=== Other flows

Two flows are worth a mention but not a diagram of their own. Notifications are the one thing on
Wolverine's durable queue: a finished sync or feed run publishes one notification, a handler fans
it out to each matching subscription, and each is rendered from a Fluid template and delivered on
its own retry schedule (1, 5 and 15 minutes, then an hour); the WebUi channel delivers it as an
in-app toast. Plex sign-in is a standard OAuth PIN flow; its notable parts, the app-owned
`User`, the first user becoming Admin, the open or closed registration gate, and per-request
session revalidation, are covered in <<section-concepts>>.
