== Building Block View

A set of .NET projects with one rule: dependencies point down toward the kernel. The
implementations never reference each other, and the presentation never references them; they meet
only through `Contracts`. `Web` is the one project that composes them.

....

Arrows are direct project references; every project reaches `Domain` transitively through
`Contracts`. Core, DB and API are peers with the same dependency
shape and never reference each other. Every project also references the `Shared` kernel, and both
`Web` and `UI` reference `Observability`; those edges are omitted to keep the graph readable.

[cols="1,3", options="header"]
|===
| Building block | Responsibility

| Shared | The kernel below everything. Monads (`Optional`, `Result`), `ValueSet`, options records, and the `AddModule<T>()` DI infrastructure. Depends on nothing.
| Domain | The pure model: entities, value objects, the media union types, and the feed, wantlist, blocklist, provider and notification vocabulary. No infrastructure. See <<section-glossary>>.
| Contracts | The seams: service, repository and provider interfaces, the record-struct ids, and DI markers. Depends on `Domain` because its signatures use domain types.
| Observability | Serilog and OpenTelemetry setup, plus the tracing helpers (`AddTracedScoped`, `AddTracedKeyedScoped`) the other layers register through.
| Core | Business logic: identifying media and merging identities, the query processor (filter, sort, limit), caching, the blocklist, the wantlist and its sync, feed runs and their cron tickers, the job queue and its runner, the `Announcer` that publishes events and notifications, sign-in and user management. Implements most `Contracts` interfaces.
| DB | Persistence: `SammlarrDbContext`, entities, repositories and migrations on SQLite, including the `Jobs` table, plus the TickerQ scheduler store in the same file. Holds secrets under data protection.
| API | One folder per external provider, each an `IServiceModule` that registers a typed HTTP client and keyed services. Also the shared HTTP resilience pipeline and the notification channels.
| Messaging | Wolverine durable messaging on SQLite, used for notifications only: the handlers that fan a notification out to its subscriptions and deliver it with retry.
| UI | Blazor components as a Razor class library: the `Features/*` vertical slices and the `Shared` cross-feature components and services. References only `Contracts`, `Shared` and `Observability`, never an implementation.
| Web | The Blazor host and composition root. Holds the root components (`App`, `Routes`) and, in `Program.cs`, the single `AddModule<T>()` wiring of every layer, plus the endpoints, health checks and host services. The one project that references every implementation and `UI`.
| AppHost | The Aspire host that runs `Web` and its dependencies for local development.
| Roslyn | Roslyn components, build-time only: source generators for the provider-subset enums and their conversions from the capability matrix and for the options-section registration, plus the analyzers, currently `SAM0001` enforcing the test naming convention.
| Analyzers | Build-time analyzers wired from the root `Directory.Build.props` into every project except `Roslyn`, its tests and itself: `SAM0002` (an `Optional` or a `Result` read by hand instead of through its helpers) and `SAM0003` (a branch on one read as a `bool`). Kept apart from `Roslyn`, whose generators inject internal types into every consumer.
|===

The load-bearing rule: `Core`, `DB` and `API` are siblings that never reference each other; when
`Core` pushes to Plex it goes through the `IMediaSink` that `API` implements, resolved by
DI. `UI` is presentation on abstractions only; `Web` is the one project that sees every
implementation and the only place they compose. `Roslyn` and `Analyzers` run at build time and ship no
runtime assembly.

=== Level 2

Two blocks are worth opening: `API`, where providers plug in, and `UI`, where features live.

==== API: one module per provider

Each provider is a folder with an `IServiceModule` that registers a typed HTTP client (wrapped by
the resilience pipeline) and keyed services against `Contracts` interfaces; `ApiModule` adds them
all.

[cols="1,3", options="header"]
|===
| Provider | Implements, keyed by provider except `IExternalIdConverter` (one enumerable of converters, each announcing its lookups)

| TMDB | `ITrendingService`, `IDetailsEnricher` (also fills ratings), `IExternalIdConverter`
| Plex | `IMediaSearchProvider`, `IMediaSink`, `IOAuthProvider`, `IDetailsEnricher`, `IExternalIdConverter`
| MDBList | `IFeedProvider`
| IMDb | nothing: `ImdbId` is reached through Plex and TMDB lookups
| TheTVDB | nothing: `TvdbId` is reached through Plex and TMDB lookups
|===

The cross-cutting folders under `API`:

* `Http`: `AddProviderHttp<TOptions>`, the resilience pipeline (per-provider concurrency gate, retry with jitter and `Retry-After`, circuit breaker, attempt and total timeouts).
* `Auth`: `IApiKeyFactory` and `ICredentialFactory`, which turn stored secrets into request credentials.
* `Notifications`: the webhook and Pushover channels and the Fluid template renderer.
* `Observability`: HTTP and provider instrumentation.

==== UI and Web: feature slices, and the host that composes them

`UI/Features` is one folder per feature area (Auth, Browse, Feeds with a live-preview editor and
a run log, Home as the library dashboard, Wantlist with per-item push status + sync, Blocklist,
Settings), each a vertical slice of
Blazor pages and components; `UI/Shared` holds the cross-feature components and services. `UI` is
a Razor class library on abstractions only, so it ships no `Program.cs` and references no
implementation.

`Web` is the host. It owns the root components (`App`, `Routes`), and its `Program.cs` is the
composition root: `AddModule<T>()` for Core, Shared, DB, API, UI and Messaging, then Wolverine,
TickerQ, authentication, the Blazor interactive server render mode (with `UI`'s assembly registered so its
pages are discovered), the auth and health endpoints, and the admin-only `/diagnostics/export`.

=== Level 3

The anatomy of a provider module, using MDBList. The whole registration is three lines:

[source,csharp]
----
services.AddHttpClient<MdblistClient>().AddProviderHttp<MdblistOptions>();
services.AddHttpClient(MdblistClient.Unauthenticated).AddProviderHttp<MdblistOptions>();
services.AddTracedKeyedScoped<IFeedProvider, MdblistService>(FeedProvider.Mdblist);
----

* `MdblistClient` is a typed HTTP client. `AddProviderHttp` gives it the resilience pipeline and a concurrency gate sized from `MdblistOptions`.
* `MdblistService` implements `IFeedProvider`, keyed to `FeedProvider.Mdblist`. `FeedProvider` is a generated subset of `MediaProvider` holding only the providers with the `Feed` capability.
* Nothing outside the folder references `MdblistService`. The feed preview resolves `IFeedProvider` by the feed's `FeedProvider` key.

Adding a provider is four steps, with no change to any consumer:

. Add an enum value and its `[Capabilities<…>]` to `MediaProvider`.
. Create an `API/<Provider>` folder with an `IServiceModule`.
. Register the typed client and the keyed service(s) against the matching `Contracts` interface(s).
. Add `AddModule<…>()` in `ApiModule`.

The capability attribute drives the generated subset enums, so the new provider shows up in the
right keyed lookups on its own. See <<section-concepts>> for the generator.
