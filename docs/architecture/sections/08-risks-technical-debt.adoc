[[section-technical-risks]]
== Risks and Technical Debt

Operational risks in what is built, and deliberately deferred work.

=== Risks in the current system

[cols="1,2,2", options="header"]
|===
| Risk | Impact | Mitigation

| Data-protection key ring | Keys persist under a stable app name (secrets survive restarts), but on the shared `/data` volume they sit unencrypted at rest and the volume must be writable by the container user or startup fails | Restrict `/data` permissions; the Dockerfile must make `/data` writable; optionally add an at-rest protector (<<section-concepts>>)
| Single instance only | SQLite, in-process Wolverine and one job runner mean a second replica contends on one file; the runner's crash recovery treats every `Running` job at startup as abandoned, which is only true with one process; the `ProviderConfig` cache has no cross-instance invalidation | Run one instance; scale-out is out of scope
| One job at a time, no deadline | Every feed run and sync shares one serial lane, and a job has no timeout, so a job that hangs stalls all queued work until the app restarts | Provider calls are bounded by the HTTP pipeline's timeouts, and id resolution's waits for a blocked provider by its `MaxWait` (once per provider per title: Plex 90 s, TMDB 15 s); a per-job deadline in `JobRunner` is the fix
| Sync push assumes clean acks | The inline drain indexes a batch by media id: a sink ack for a title it was not sent, or a second ack for one, throws and fails the sync job, and the same batch fails every later sync | None yet; guard the lookup in `WantlistSyncEngine.ApplyBatchAsync`
| In-app notifications not backfilled | The WebUi target's subscriptions are seeded only when a user is created, so users created before a notification type was added to the seed (feed-run completed and failed) never get that toast | Subscribe it by hand in Settings, or add a data migration
| Plex `ById` 429 storm | Under rate-limiting many titles cannot be identified and show as "not found" for that run | Concurrency gate + `Retry-After` reduce it, a blocked Plex is waited for once per title (at most its `MaxWait`) instead of asked per title, and the ids are not cached unmatched; a fuller fix is deferred (below)
| Identity merge on one shared id | Within a flush, two same-type titles a provider tags with the same or a conflicting external id merge into one row, since a single shared `(Source, Type, Value)` is enough and there is no multi-id agreement check. MediaType still separates a movie from a show, and a collision bridging two already-stored rows throws | Provider ids are trusted; a multi-id agreement or intra-flush same-type conflict check is possible hardening if a provider proves unreliable (scenario C)
| TMDB feed capability unimplemented | `MediaProvider.Tmdb` has the `Feed` capability so `FeedProvider` includes it, but no `IFeedProvider` exists; selecting it fails | Drop `Feed` from TMDB, or implement a TMDB feed service. Only MDBList feeds work
| Build needs Node | `dotnet build` of `Web` runs `npm ci`/`npm run css` to generate the gitignored `app.css`, so a machine, CI runner or image build stage without Node cannot build the app | Install Node wherever the app is built; the release pipeline and Dockerfile must include it
|===

=== Deferred and planned work

[cols="1,3", options="header"]
|===
| Item | State

| Job queue surfacing | Deferred. The queue shows your own jobs on Home, but not other users' occupancy (`QueueSnapshot.OthersPending` is computed and unrendered); a run whose planning throws is never recorded, so the feeds list keeps showing the previous run and only the failure notification tells; and an abandoned push has no retry action.
| Media-sinks redesign | Planned (`branding-logo-refresh`, Phases 4 and 8 to 11): direct Radarr/Sonarr sinks beside Plex, and the Wantlist to Wantlist/Sink rename. Builds on the inline push that has shipped (<<section-runtime-view>>).
| E2E circuit crash | Unexplained: roughly one full E2E run in five trips the session-level circuit-crash guard while all tests pass. Not reproduced with output captured, so no stack trace yet.
| Result-based error handling | Planned (`retire-control-flow-exceptions-to-result`): replace control-flow exceptions with `Result` at the service boundaries.
| Metrics | Not implemented; only logs and traces over OTLP.
| Release pipeline | Not built. CI/CD, the image, GHCR releases (Aspire-driven, Option A) and the update check belong to the release-engineering plan. The build already stamps its version from git tags with MinVer and shows it in Settings › About and the footer.
|===
