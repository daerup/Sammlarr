# 8. Risks and Technical Debt

Operational risks in what is built, and deliberately deferred work.

## Risks in the current system

| Risk | Impact | Mitigation |
|---|---|---|
| Data-protection key ring | Keys persist under a stable app name (secrets survive restarts), but on the shared `/data` volume they sit unencrypted at rest and the volume must be writable by the container user or startup fails | Restrict `/data` permissions; the Dockerfile must make `/data` writable; optionally add an at-rest protector ([Cross-cutting Concepts](06-crosscutting.md)) |
| Single instance only | SQLite, in-process Wolverine and one job runner mean a second replica contends on one file; the runner's crash recovery treats every `Running` job at startup as abandoned, which is only true with one process; the `ProviderConfig` cache has no cross-instance invalidation | Run one instance; scale-out is out of scope |
| One job at a time, no deadline | Every feed run and sync shares one serial queue, and a job has no timeout, so a job that hangs stalls all queued work until the app restarts | Each attempt is bounded by its attempt timeout and its retries; a lane refuses an attempt whose wait for a block outlasts the service's `MaxWait` (Plex 90 s, TMDB 15 s), enrichment takes a blocked service only within its `EnrichWait` (TMDB 15 s, Plex never), and a list load's watchdog settles every open title couldn't look up once nothing has settled for `StallAfter` (3 minutes); a per-job deadline in `JobRunner` is the fix |
| Sync push assumes clean acks | The inline drain indexes a batch by media id: a sink ack for a title it was not sent, or a second ack for one, throws and fails the sync job, and the same batch fails every later sync | None yet; guard the lookup in `WantlistSyncEngine.ApplyBatchAsync` |
| In-app notifications not backfilled | The WebUi target's subscriptions are seeded only when a user is created, so users created before a notification type is added to the seed never get that toast | Subscribe it by hand in Settings, or add a data migration |
| Plex 429 storm | Under rate-limiting, titles that need Plex settle "couldn't look up" for that run | Each Plex route is paced by its own lane (match at 300 per minute and 5 in flight, metadata and the rest of the API at 50 per second and 25 in flight, the watchlist at 4 in flight; Plex publishes no limit, so these are settings, not promises), a new title costs one match call, a 429 blocks or slows only its lane and no retry goes into the block, a title waits for Plex in the lane only within its `MaxWait`, titles that need nothing from Plex settle meanwhile, and the ids are not cached unmatched, so the next run retries them |
| Plex's match endpoint is undocumented | Plex ids come only from `library/metadata/matches` on the discover host, which Plex does not document. If Plex changes it, every new title for a Plex sink fails to identify: a 404 or an empty answer reads as a miss, settles the title "not found" and is cached for an hour; a 5xx settles it "couldn't look up". The Search page is unaffected, since it uses Plex's title search | The endpoint is the one Pulsarr matches by id with; `PlexMatchTests` pin one call per title, and the E2E suite answers the endpoint from a mapping generated from recorded Plex metadata (`plex-discover/library-metadata-matches.json`), which pins Sammlarr's side of the format, not Plex's; a run where every Plex title settles "not found" points at the endpoint; the planner still plans `ByHints` lookups, so Plex's title search could come back as a fallback lookup without touching the resolver |
| Identity on one shared key | A claim extends a stored title on one shared identity key, with no multi-id agreement check, so two different titles a provider tags with the same key become one row. Ids that would join two stored titles never merge them: the title settles unmatched as a conflict and the run completes, and an enricher's key that would join two titles is dropped from the title it was found for. A title stored twice stays twice, and its later entries keep settling as conflicts, until the nightly pass merges the pair; a pair no second source can answer stays twice | Provider keys are trusted; rating page slugs are no keys, so remakes never meet on a shared slug (ADR 0018); every pair a claim meets is noted, and the nightly housekeeping pass merges it once a source outside the claim's own maps one title's id to the other's (`DuplicateTitles`); a multi-id agreement check is possible hardening if a provider proves unreliable (scenario C) |
| Trakt's API Use Policy | Trakt permits a self-hosted tool on its own credentials but forbids mirroring its lists or redistributing its data as a feed for other services, and has blocked services (MDBList, SIMKL) without notice; it also deletes an API app after 30 days without use | Each person brings their own client ID, Sammlarr reads only public watchlists, lists and charts for that person's own wantlist and never passes Trakt data on, and the key row says the app must stay in use |
| Trakt's rate for every title | With a Trakt client ID stored, a title holding a Trakt or IMDb id but no Trakt rating asks Trakt, one request each on Trakt's lane of 1,000 per 5 minutes, so a large first load without MDBList's Trakt rating waits on Trakt | The reader keeps each answer for the load under every id it carries; MDBList, when its key is set, usually fills the Trakt rating first |
| AniList's rate for anime from every feed | Every anime a feed brings, from any source, asks the AniList enricher, so a large anime-heavy feed's details wait on AniList's lane of 30 requests a minute while it runs degraded | `AniListTitles` keeps the titles a feed page read and asks the rest on its batching lane, 50 ids a query |
| MDBList's daily budget | MDBList allows a key 1,000 requests a day: a large feed and enrichment share it, and a spent budget answers that key's calls with 429 for the rest of the day | Title lookups stop at the last `MDBList:FeedReserve` requests of the day (`appsettings.json` sets 50), which stay for list pages, and warn once per reset when they start holding back; the FillDetails job stops once less than half the day's allowance is left; only titles whose needed MDBList fields are missing are asked, 200 a request, so a fully cached run sends only its list pages; each API key has lanes of its own, so a 429 that says one key's quota is spent blocks nothing else, and every attempt's answer, that 429 included, updates the key's budget, so its lookups stop until the reset |
| Lists through MDBList's external lists | IMDb and Letterboxd lists are feeds only as MDBList external lists (ADR 0012; Trakt has its own feed since the provider expansion's Phase 21): a free MDBList account adds one, refreshed weekly, and an owner's lists stop updating 120 days after their last login | Documented in the feed help; a supporter account lifts the limits; nothing else reads IMDb's or Letterboxd's lists |
| Fribb's anime id map has no licence | `anime-list-full.json` comes from a repository that declares no licence, so no right to it is granted | Sammlarr downloads it at runtime and never ships it, and the Data sources row says so; the release licence gate must carry the same note |
| Shared datasets hold the write lock | Replacing IMDb's 1.7 million ratings takes the SQLite write lock for a few seconds a day (2.5 s measured), longer on slow disks, against the 5 s `busy_timeout`; the compaction after it adds a `VACUUM` when a tenth of the pages are free, which rewrites the whole file under the write lock (0.5 s on the dev file) and needs about the file's size free on disk | The loads run at 04:30 server time (TickerQ reads a cron in the server's zone), after the nightly housekeeping pass's own compaction at 03:00, one at a time through `DatasetGate` (a first load TickerQ starts twice waits, then finds the file unchanged); a `VACUUM` that fails (disk full, busy) is logged and leaves the free pages for the next load's compaction; a slower disk would need a staged swap |
| Build needs Node | `dotnet build` of `Web` runs `npm ci`/`npm run css` to generate the gitignored `app.css`, so a machine, CI runner or image build stage without Node cannot build the app | Install Node wherever the app is built; the release pipeline and Dockerfile must include it |

## Deferred and planned work

| Item | State |
|---|---|
| Tooltip guard | Workaround for BlazorBlueprint 4.1.0: `Web/wwwroot/js/tooltip-guard.js` keeps a `tooltip-*-trigger` from opening on a focus that no Tab caused (a click, a dialog handing focus back), and hides a tooltip portal whose close reached the browser before its render and left it visible. It relies on BlazorBlueprint's trigger ids and portal markup (`UiInvariantTests` fails if they are renamed). A screen reader's virtual cursor or swipe moves focus without a Tab, so it no longer gets the tooltip text. A tooltip trigger nested in another trigger must use `AsChild="false" Class="inline-flex" Focusable="false"`, or it takes the parent's id and the guard misses it. Three upstream issues are drafted, not filed yet: focus without a Tab, the close racing its render, and a leave processed after the show timer, which the guard does not cover. BlazorBlueprint fixed the first two for `BbCopyText` only (#512, #471). The script, its line in `Web/App.razor` and `Tooltip_WhenItsCloseWasAbandoned_Hides` go once a release fixes the first two for `BbTooltip`. |
| Job queue surfacing | Deferred. The queue shows your own jobs on Home, but not other users' occupancy (`QueueSnapshot.OthersPending` is computed and unrendered), and an abandoned push has no retry action. |
| E2E circuit crash | Unexplained: roughly one full E2E run in five trips the session-level circuit-crash guard while all tests pass. Not reproduced with output captured, so no stack trace yet. |
| Result-based error handling | Backlog: wantlist and blocklist writes return a `Result` instead of throwing. Lookups already answer instead of throwing (`Answer<T>`), and an identity conflict is a claim outcome. |
| Metrics | Not implemented; only logs and traces over OTLP. |
| Release pipeline | Partly built. `Web/Dockerfile` builds the image and `release.yml` pushes it to GHCR on a `v*` tag, which release-please creates; CI, the scans, signing and SBOMs belong to the release-engineering plan. The build stamps its version from git tags with MinVer and shows it in Settings › About and the footer, and a release build asks GitHub for the latest release at most every 12 hours to show an update badge there (a dev or staging build never asks). |
